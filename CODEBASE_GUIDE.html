What this app is

This codebase runs the website for a charter bus company. It's the digital version of "call the office to book a bus" — except now customers fill out a form online, office staff review and price the request, and the assigned driver sees their trip details on their own screen.

Everyone who uses the app falls into one of three roles, and almost every page and permission in the system exists to serve one of them:

Customer

A school, church, or group that wants to book a bus. They fill out a quote request, wait for a price, and confirm or manage their booking.

Driver

Company staff who drive the buses. They check which trips they're assigned to and log a safety checklist before each one.

Admin

Office staff who review quote requests, set final prices, assign a driver and bus to each trip, and manage the fleet.

Visitor

Anyone browsing the public website before they've signed up — sees the homepage, "About," and can start a quote.

The 30,000-foot view

The big picture

A lot of websites you've used have three layers: something in your browser, a company's own server in the middle, and a database at the back. This app skips the middle layer. The website (what you see in your browser) talks almost directly to a cloud database service called Supabase, which handles storage, logins, and — importantly — the rules about who's allowed to see or change what. Think of Supabase as "the filing cabinet, the front-desk security guard, and the calculator" all in one hosted service, rather than the company having built its own back-office server from scratch.

Two consequences of this design that are worth knowing, because they explain a lot of the folder structure you'll see next:

  • The "rules" mostly live in the database, not the website. Things like "how much does a trip cost" or "can this person see this booking" are decided inside Supabase, so the website is more of a window into the data than the thing in charge of it.
  • Small helper programs ("edge functions") fill the gaps Supabase's database can't send an email on its own, so a tiny helper program (notify-send) does that one job.

Inside src/routes/ — the pages

This project uses something called file-based routing: each file in this folder automatically becomes a page at a matching web address. For example, the file quote.tsx becomes the page at yoursite.com/quote. There are 11 pages total — they're all explained one by one in the next section.

Inside supabase/migrations/ — the database's history book

A migration is a small, dated instruction file that changes the database's structure — like "add a new filing cabinet for invoices" or "add a new drawer to the existing quotes cabinet." There are about 51 of them, applied in order from oldest to newest, so together they tell the full story of how the database grew over time. Grouped by theme:

Core booking data

People & login roles, bus fleet, drivers, schools/customers, quotes, quote versions, trips, invoices, payroll.

Pricing configuration

The literal price list — hourly rates by bus size and surcharges (fuel, overtime, long-distance, GST) — kept as data, not hardcoded numbers.

Trip assignment

Which driver is certified for which bus size, who's available on which day, and rules against pairing certain drivers together.

Notifications & special trip types

The outgoing-email queue, plus extra tables for "shuttle" trips (repeated runs) and "multi-destination" trips (several stops).

Inside supabase/functions/ — the helper programs

notify-send supabase/functions/notify-send/index.ts

The "mail carrier." The database can only write down that an email needs sending; this program actually sends it, using an email delivery service called Resend. If the delivery key isn't configured yet, it just leaves emails queued rather than breaking anything.

invite-driver supabase/functions/invite-driver/index.ts

How an admin adds a brand-new driver account: sends them an invite email and creates their login + driver record. Deliberately locked down so only admins can create new accounts with elevated roles.

Following one booking

From quote to trip

Here's the life of a single booking request, start to finish, and which page/piece of the system is responsible at each step:

1
Customer fills out the form at /quote and submits it.
2
The database creates a quote and its first version (a locked snapshot of the details + price at that moment), and queues confirmation emails.
3
It shows up in the admin Quotes queue for office staff to review and finalize the price.
4
Admin approves it — this creates an invoice and emails the customer their price. (Or rejects it, which cancels the request and notifies the customer.)
5
Customer confirms they accept the price, from their /portal dashboard.
6
Admin assigns a specific driver and bus — the system suggests available options and avoids double-booking.
7
The booking becomes an official trip and now appears on the assigned driver's /driver dashboard.
8
Driver completes their pre-trip checklist and runs the trip; afterward, actual times/mileage get logged for records.

The part everyone asks about

How a price gets calculated

Pricing logic lives entirely inside the database, in a function called calculate_estimate() — not scattered across website code. That matters because it means there's exactly one place where "how much does this cost" is decided, so the number a customer sees can't quietly drift out of sync with what the office actually charges. Think of it as a recipe the database always follows, in order:

  1. Count the seats needed. Younger kids (Kindergarten–Grade 4) count as ⅓ of a seat; everyone else counts as ½ a seat.
  2. Pick a bus size — 18, 47, or 56 seats — big enough for the group (and how many buses, if the group needs more than one).
  3. Look up the hourly rate for that bus size and the customer's membership tier (member / non-member / church).
  4. Work out driver hours — the trip's actual time window, plus a fixed 1-hour buffer for driver travel.
  5. Apply a minimum-hours floor so short trips still cover a base charge.
  6. Add surcharges — fuel (flat fee, can be waived by an admin), overtime (past a certain number of hours), and long-distance (past ~200km one-way).
  7. Add 5% GST on the subtotal.
  8. Save and return the total, along with a full breakdown, so the price shown always matches what's stored.

Trust & safety

Who can see what

Every table in the database has a feature called Row Level Security (RLS) turned on — think of it as a bouncer standing at every filing cabinet, checking ID before letting anyone look inside or change anything. It's enforced by the database itself, not just by the website hiding buttons, which is what makes it trustworthy.

RoleCan see / do
CustomerOnly their own quotes, versions, invoices, and trips.
DriverTheir own driver record, availability, and the trips assigned to them.
AdminEverything — the only role allowed to see and manage all records.
VisitorPublic pricing info only (so the quote form can show an accurate live estimate before anyone signs up) — nothing containing personal information.

A real story: catching a security bug

Two migrations (026 and 028) fixed a genuine security hole worth knowing about, because it's a good example of "software development involves finding and fixing real problems, not just adding features":

Originally, when someone signed up, the system trusted whatever "role" they claimed to be — meaning a customer could theoretically sign up and tell the system "I'm an admin," and it would believe them. This was fixed so every new signup is always forced to customer, no exceptions; only an admin (or the driver-invite process) can grant a higher role. A second, sneakier version of the same bug was then found — even after that fix, a logged-in user could still try to sneak a role change into an unrelated "update my profile" request. That was closed with a database-level rule that flatly refuses to let anyone but an admin change a "role" field, no matter how the request is phrased.

Reference

Glossary of terms

Route / page
A single screen in the app, tied to a web address, defined by one file in src/routes/.
Component
A reusable chunk of a page — a button, a form field, a whole quote-form section — that can be reused across pages instead of rebuilt each time.
Database / table
Structured storage, organized like a spreadsheet with named columns — e.g. the "quotes" table has one row per quote request.
Migration
A dated instruction file that changes the database's structure over time — the database's own change history.
Supabase
The hosted cloud service this app uses for its database, logins, and permission rules — this app doesn't run its own separate server.
RLS (Row Level Security)
Database-enforced rules about who can see or edit which rows of data, based on who's logged in and their role.
Edge function
A small standalone program that runs in the cloud to do something the database can't do on its own, like sending an email.
RPC (remote procedure call)
The website asking the database to run one of its built-in named actions (like "approve this quote") rather than editing raw data directly.
API key / environment variable
A private password-like value (e.g. for the email service) kept out of the website's public code and configured separately.
Git / branch / commit
The tool used to track every change made to the code over time, and to work on new changes safely without touching what's already live.
